# v0.1.0 ships only FFI cores — nothing for the Aether-source consumer

**From:** the datastar-aether line, 2026-09-18. About the `v0.1.0` release.
**Status:** a positioning observation, not a bug. Small ask. **Blocked on the
companion ask, which is DECIDED as fix B (wait on upstream) — so this stays
pending until `ae` gains root-export and we add the `aether.toml`. The
FFI/Aether-source distinction (item 2 below) can be added to the release notes
now, independent of the manifest.**

## What the release ships

`v0.1.0` (pre-release, on the `reboot` lineage) attaches per-platform
prebuilt cores and nothing else:

```
libphonenumber_ae-v0.1.0-linux-x86_64.so      (+ macos/windows/freebsd, arm64/x86_64)
…each with a .sha256, and .dll.lib import libs on Windows
```

Plus `get-core.sh` to fetch the right one. That is exactly what the **20
language bindings** need — they `dlopen` the core over the C ABI. Good.

## The gap

There is a **second, first-class consumer**: an Aether program that wants
to `import` the engine as source and compile it in-graph — no `.so`, no
FFI. This is the path this repo's own `aether/` binding takes ("the one
binding with NO FFI"), and the one datastar-aether wants for its phone
component.

For that consumer the release offers nothing:

- no `[package] modules` manifest, so `ae add
  github.com/aether-lang-dev/libphonenumber-ae` doesn't resolve the
  engine onto the module search path (see the companion ask —
  `aether-source-consumption-needs-a-way-to-export-the-package-root.md` —
  for why a manifest alone isn't enough here);
- the release notes don't mention the source path at all, so a reader
  concludes the only way in is the `.so`.

## The ask

Once the root-export blocker is resolved (companion ask), make the
Aether-source path a declared, released thing:

1. Ship the `[package] modules` manifest so `ae add …@v0.1.x` resolves
   `import phonenumber` (or `core.phonenumber`, per whichever fix lands)
   with no `--lib` — the way `ae add github.com/aether-lang-dev/selaenium`
   already works.
2. One line in the release notes distinguishing the two consumption
   models: **FFI** (fetch a prebuilt core, for the language bindings) vs
   **Aether-source** (`ae add`, compile the `.ae` graph in-process, for
   Aether consumers).

The prize is the same as selaenium's: an Aether consumer names one
dependency in `aether.toml` and imports the engine, no path knowledge, no
native artifact to place. datastar-aether would be the first such
consumer and can be the test case.

## Not urgent

Blocked on the companion ask anyway. Filed together so the release's
consumer story is complete once both are addressed.
